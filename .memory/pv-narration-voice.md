title: PV ナレーション音声を全シーンで同じ声に保つ方法（pr/pv）
updated: 2026-07-30
status: active
---

`pr/pv` の PV は9シーン分のナレーションを Irodori-TTS（MIT）でローカル生成する。
「同じ設定なのに声が違う」問題に2周はまったので、原因と決着を残す。

対象は次の4つ。

- `pr/pv/scripts/generate-narration.mjs` — 生成本体。声の仕様はここにある
- `pr/pv/scripts/voiceprint.py` — 計測の実装（ピッチ・包絡・帯域バランス・HNR・hiss）
- `pr/pv/scripts/pick-reference.py` — 参照候補から1本を選ぶ
- `pr/pv/scripts/check-narration-voice.py` — 完成した9本を検証する

## 1. caption は「声の種類」を決めるが「個体」を決めない

Irodori-TTS の VoiceDesign は caption（「20代半ばの男性のナレーター…」など）で声を指定する。
これは**どんな声かは縛るが、どの個体かは縛らない**。

seed を固定しても効かない。seed が同じでもテキストが違えば別人になる。
実測: 同一 caption・同一 seed で4行を生成し、中央値ピッチ **115〜167Hz**。別人と言える幅。

**個体を固定する唯一のパラメータは話者参照**（`irodori.ref_wav` / `ref_latent` / `ref_embed`、
または `POST /v1/audio/voices` で登録した `voice` ID）。

## 2. 生成はバイト単位で決定的

`(input, caption, num_steps, seed)` が同じなら**同一バイト列**が返る（SHA-256 で確認）。

この性質のおかげで**参照音声もコードから決定的に再生成できる**。
リポジトリに wav を置く必要がない。`generate-narration.mjs` が声の完全な仕様になっている。

## 3. パラメータは `irodori` の中に入れる

`POST /v1/audio/speech` のスキーマでは `caption` / `num_steps` / `seed` などは
`irodori` オブジェクトの中。直下に置いても現状のサーバーは受け付ける（実測で同一出力）が、
保証はスキーマ側にしかない。`speed` と `voice` と `response_format` だけが直下。

スキーマ全体は `curl http://127.0.0.1:8088/openapi.json` で取れる。

## 4. F0 で声色は測れない — この計測ミスで1周無駄にした

最初の対策は「1行あたり6テイク生成し、中央値ピッチが目標135Hzに最も近いものを採用」だった。
自分の指標では成功していた（9本のピッチ幅 11.5Hz）。**しかし声は揃っていなかった。**

声の同一性は基音ではなく**スペクトル包絡（フォルマント）**に宿る。
同じ135Hzでも別人になり得る。ピッチだけ揃えても解決しない。

そのとき実際に起きていたこと:

| 指標 | 値 |
| --- | --- |
| ピッチ幅 | 11.5Hz（揃って見える） |
| 声色（包絡）の平均ペア距離 | **6.25dB** |
| 帯域バランスの振れ | **14.6dB**（+18.06 〜 +32.70dB） |

`check-narration-voice.py` はピッチと包絡と帯域バランスを出す。**包絡を見ること。**

**絶対値では判断できない。** 文が違えば音素が違うので、同一話者でも距離はゼロにならない。
1本を前半後半に割って比較した下限は平均 5.07dB。
**同じ行を別設定で生成して比べる**用途にのみ使う（音素由来の下限が両者で相殺される）。

## 5. 参照は長くしないほうが良い（直感に反する）

「参照は長く音素豊富なほど個体固定が強まる」は**外れ**。実測で悪化した。

| 参照 | ピッチ幅 | 声色平均 |
| --- | --- | --- |
| 1文 7.5秒 | 11.2Hz | **4.11dB** |
| 3文 18.3秒 | 12.4Hz | 4.47dB |

1本のきれいな読みのほうが的が絞れる。`REFERENCE_TEXT` を増やそうと思ったら、まずこれを思い出すこと。

## 6. 「ガビガビ」の原因は参照音声の高域ノイズ。参照は測って選ぶ

**参照が持つノイズは、そこからクローンした全行に転写される。** 参照が出力の床を決める。

同一設定・seed 違いの候補8本を測ると、8kHz以上の余剰エネルギー（hiss）が
**-31.5dB から -56.4dB まで25dB ばらつく**。測らずに1本目を採ると汚い側を引く。

| 対象 | hiss |
| --- | --- |
| 測らずに採った参照 | -32.7dB |
| その出力 | -39.8 〜 -40.2dB |
| 3文連結の長い参照 | -33.5dB → 出力も -33.5dB（最悪） |
| 参照なし（caption のみ） | -46.8dB |
| 測って選んだ参照 | -53.8dB → 出力 平均 -49.3dB |

公式ドキュメントも "Short, clean references may work well, but the more important
point is to avoid music, noise, or multiple speakers" と "If artifacts increase,
back off the scale" と書いている。

**選定規則を一度間違えた。** hiss だけで選ぶと、最も静かだが**倍音が最弱**の候補
（HNR 0.42dB）を引き、出力がかえって粗くなった（HNR 2.58 対 3.62dB）。
静かなことと芯があることは別。**-50dB（可聴域下）を満たす候補の中で HNR 最大**を採る。
`scripts/pick-reference.py` がこれをやる。

**相関:** ピッチが高いテイクほど汚い（150〜155Hz → -31〜-35dB、133〜137Hz → -43〜-56dB）。
以前の「スカった声」も同じ現象だった可能性が高い。

**参照は -16 LUFS / -3 dBTP に条件付けして 32bit float で書く。**
サーバーは参照を既定で -16 LUFS に正規化するので、-17.8 LUFS・ピーク -0.04 dBTP の
生出力を渡すとフルスケール超えの方向へ持ち上げられる。また16bitで書くと
レベル低下ぶん量子化ノイズが浮く（同一クリップが 3dB 悪化した）。

**caption を絞る必要はなかった。** VoiceDesign モデルカードは「参照と caption を併用して
矛盾させると不安定になる」「caption は声質でなく style を指定せよ」と警告するが、
参照がクリーンなら full caption が最良だった。支配要因は参照の品質。

**`num_steps` は 40。** 64 は測定で劣り（ノイズ -61.32 対 -61.95dB、粗さ 2.44 対 2.52dB）
1.6倍遅い。公式の目安も 32〜40 で、40 が高品質用。

## 7. 音質そのものの上限はモデル側にある。設定では上がらない

「音割れ・低品質」の訴えを調査した結論。**サーバー側の設定では改善しない。**

まず指標を校正した。完全に周期的な信号でも HNR は 6.5dB で飽和し、SNR 10dB で 4.7dB、
6dB で 2.9dB。そのうえで**同一の文を別の合成器で作って比較**したのが決定的だった:

| 音源 | HNR | 帯域上端 |
| --- | --- | --- |
| Windows SAPI（Haruka） | **+7.84dB** | 10.0kHz |
| Irodori-TTS | **+3.17dB** | 12.8kHz |

約5〜9dB相当の非周期エネルギーが**音声帯域の内部**にある。だから後処理で消せない
（6kHz まで低域だけ残しても 3.17 → 3.32 しか動かない）。

掃引結果（s04、1行での比較）:

| 設定 | HNR | hiss |
| --- | --- | --- |
| baseline 40 steps | +3.21 | -49.00 |
| 100 steps | +3.24 | -47.58 |
| 160 steps | +3.05 | -47.28 |
| cfg_scale_text 4.5 | +3.21 | -49.40 |
| cfg_scale_text 2.0 | +3.28 | 帯域が 8.5kHz に劣化 |
| truncation_factor 0.9 | +3.43 | -48.39 |
| rescale k0.7 sigma1.0 | +3.00 | -43.82 |
| num_candidates 4 | +3.21 | -49.00（baseline と完全一致＝無効） |
| sway schedule | +3.42 | -48.19 |

**最良でも +0.2dB。** `num_candidates` はこのチェックポイントでは効いていない。

**唯一効くのは参照音声の品質。出力は参照の値をほぼ追随する:**

| 参照 | 参照の HNR | 出力の HNR |
| --- | --- | --- |
| Irodori 自身の出力 | 1.32dB | 3.17dB |
| 別の合成器（Windows 男性） | 4.29dB | **4.04dB** |

つまり**人間の声を録って参照にすれば音質そのものが上がる**。一貫性のためだけの手段ではない。

その他の観測: 出力は約 **12.8kHz で帯域が切れる**（48kHz コンテナに実質24kHz相当）。
11〜12.5kHz にクリーンな合成音には無い持ち上がりがある（s02 で +15dB）が、
絶対値 -39〜-53dB なので主因ではない。

### 追記: このチェックポイントは女性の声のほうが明らかにきれい

caption の**性別の語だけ**を 男性 → 女性 に変えて9本を作り直した結果（他は完全に同一）:

| 指標 | 男性 | 女性 |
| --- | --- | --- |
| 粗さ HNR | 2.66〜4.32（平均 3.16） | **6.08〜7.76（平均 6.87）** |
| ノイズ hiss | 平均 -49.2dB | **平均 -62.7dB** |
| 声色の包絡 | 2.93dB | 3.22dB |

**HNR +3.7dB、hiss -13dB。** 設定の掃引で得られた最大 +0.2dB とは桁が違う。
Windows SAPI（7.84dB）にほぼ並ぶ水準。

参照候補の段階で既に差が出ている。男性プールの HNR は 0.42〜1.52dB、女性は 4.06〜5.75dB。
一方 hiss は女性のほうが悪く（-25.97〜-51.59、男性は -31.51〜-56.36）、
**-50dB を満たす候補が1本しか出なかった**ので、候補数8はぎりぎり。減らさないこと。

**男性の声で品質に悩んだら、まずこの差を思い出す。** モデルの弱いモードと戦っていた可能性がある。

## 8. `cfg_scale_speaker` は既定の 5.0 を使う。下げても薄さは防げない

以前**合成音を参照にしてクローン**したとき「スカった声」になり、クローン自体を捨てた。
そのとき「既定 5.0 が参照に追従しすぎたせいだ」と考えて 3.0 に下げたが、**これは逆だった**。

9行で測ると単調に「高いほど一貫」で、しかも 3.0 が**最も薄い**:

| cfg | 声色 平均 | 声色 最悪 | 帯域バランスの下限 |
| --- | --- | --- | --- |
| 3.0 | 3.84dB | 6.97dB | +20.87dB（最も薄い） |
| **5.0** | 3.77dB | 6.58dB | +21.68dB |
| 7.0 | 3.57dB | 5.90dB | +22.14dB |

7.0 がさらに良いが、モデルの既定を超えたガイダンス値は拡散モデルが破綻し始める領域。
差 0.27dB のために踏み込む価値はないと判断して 5.0。

**4行だけの実験では 3.0 と 5.0 の差が出なかった。** 9行必要だった。設定比較は全行でやること。

## 9. 残るピッチ差 約30Hz は抑揚であって話者のぶれではない

クローン後も文ごとの中央値ピッチは 126〜157Hz に散る。これは直さない。根拠3つ:

- **参照の強さを変えても動かない**（cfg 3.0/5.0/7.0 で 30.0 / 33.2 / 30.1Hz）。
- **外れる行が毎回同じ。** s02 が常に最低（約126Hz）、s03 が常に最高（約157Hz）。
- **seed を振っても動かない。** s03 は4つの seed すべてで 155.8〜161.1Hz（幅 5.2Hz）。
  つまり**テキストが音域を決めている**。seed 探索を実装しても無駄。

そして 1文の中で F0 は **62.4Hz** 動いている（中央半分だけで）。文間の差 30Hz はその半分以下で、
各文の音域はほぼ重なる（どれも約110〜185Hz）。人の朗読でも起きる範囲。

旧方式の「ピッチ幅 11.5Hz」は良い声だったのではなく、**その数値を選別基準にしていたから小さかった**だけ。

## 10. `loudnorm` は必ず2パスで使う

1パスの `loudnorm` は**聴きながら補正する**ので、ゲインがファイル内で動き、着地点もばらつく。
3.4秒の短い行では補正が落ち着く前に終わる。

`print_format=json` で測ってから `measured_*` と `offset` を渡し、`linear=true` を付ける。
これで**ファイル全体に単一の線形ゲイン**がかかり、音量も音色も動かない。

実害の実測: 1パスで「-14 LUFS に正規化」した9本を測り直すと **-14.77〜-15.87 LUFS**。
狙いより約1.4dB 小さく、1.1 LU ばらついていた。

## 11. 設定を変えたら全部作り直す仕組みを入れてある

`generate-narration.mjs` は設定のフィンガープリントを `pr/pv/out/narration/settings.json` に書く。
一致すれば既存ファイルを飛ばして再開、変われば**9本すべて再生成**する。

「設定を変えたのに一部だけ古い声のまま」という混在を機構で防ぐため。
9本が9通りの声になった原因の一部はこれだった。

## 到達した数値

| 指標 | 当初（参照なし＋ピッチ選別） | 汚い参照からクローン | **現行（測って選んだ参照）** |
| --- | --- | --- | --- |
| 声色（包絡）の平均ペア距離 | 6.25dB | 3.81dB | **2.83dB**（下限4.8を下回る） |
| 帯域バランスの振れ | 14.6dB | 6.2dB | **3.4dB** |
| 粗さ HNR の最低値 | — | 0.94dB | **2.66dB** |
| ノイズ hiss の平均 | — | -37.5dB | **-49.3dB** |
| 実測ラウドネス | -14.77〜-15.87 | -14.43〜-15.05 | **-13.95〜-14.88** |
| ピッチ幅 | 11.5Hz（過適合） | 30.0Hz | 18.7Hz（抑揚由来・許容） |

ラウドネスがぴったり -14 に揃わないのは仕様。真のピークが **-1.50 dBTP に張り付く**ので、
リミッターではなくピーク上限がゲインを縛っている。圧縮して押し上げると音色が
不均一に変わるので、そちらは選ばない。AAC 再エンコードでピークは上がるため -1.5 のまま。

参照をクリーンにしたら高域が減り、ピークの余裕が増えたぶん -14 に近づいた。

## 映像全体は -14 LUFS に揃える（`export-web.sh` がやる）

**ナレーションが -14 でも映像は -11.4 LUFS になる。** モノラル音声を Remotion が左右に
複製し、BS.1770 はチャンネルを合算するので +3.01dB 上がる。

クリップはしない（ピーク -1.5 dBFS）が、標準より2〜3dB大きい音はノートPCやスマホの
スピーカーを歪ませる。**これを「音割れ」と認識しうる。** LP の `<video>` は正規化しない。

`export-web.sh` がマスターを2パスで -14 LUFS に揃える。映像ストリームはコピーなので
画質は無劣化。音声は再エンコードが必要なので、**既に目標値なら何もしない**ガードがある
（二重に AAC を通さないため）。この処理による音質劣化は測定して無いことを確認済み。

## 未解決

- 声質そのものの良し悪しは計測できない。ユーザーの耳による判定が必要。
- **人間の声を10秒ほど録って参照にする**のが残る最大の手。7. のとおり、一貫性だけでなく
  **音質そのもの**が上がる（出力の HNR は参照の HNR を追随する）。
  合成音を参照にすることで生じる劣化が原理的に消える。
- それが無理なら別チェックポイント（500M-v3 系）か別エンジンの検討になる。
