# Settings, Localization and UI Design Contracts

## Settings surface

The current native Settings tab (`src/app/(tabs)/settings/index.tsx`) presents **five destination screens** and **one in-place maintenance operation**:

| Screen/row | As-built functionality | Owner |
| --- | --- | --- |
| Calendar | First weekday Monday or Sunday, persisted as `weekStartDay` | `src/app/settings/calendar.tsx` |
| Techniques | View, add, delete and reorder technique names; seeded defaults are not re-created after intentional deletion | `src/app/settings/techniques.tsx`, `techniqueOptionRepository` |
| Favorite resorts | Search/select/add/remove names used for fast resort suggestions | `src/app/settings/favorite-resorts.tsx` |
| Tags | Add/remove `custom` tags; deleting one removes related video associations | `src/app/settings/tags.tsx` |
| Duplicate candidates | Compare videos, inspect similarity groups, select and confirm deletion | `src/app/settings/duplicate-candidates.tsx` |
| Remove unused files | Confirmation -> cleanup -> result count/error alert; prevent concurrent taps | `cleanupOrphanedFiles` |

A small backup note explains reliance on OS iCloud Backup. The screen **does not** expose file-based export/restore, a storage/data priority selector, automatic iCloud Drive synchronization, or Photos asset relinking. A native implementation module existing elsewhere is not evidence of a shipped Settings control.

## Technique and tag vocabularies

Techniques: `DEFAULT_TECHNIQUE_OPTIONS` is a fixed initial vocabulary oriented toward skiing and snowboarding. At startup, `planTechniqueSeed` compares existing items with `technique_defaults_seeded` so a default deliberately deleted by the user **stays deleted**. Technique display ordering is persisted through `sort_order`. A video's chosen techniques are **embedded name strings** in its `videos.techniques` JSON field; deleting a vocabulary option **does not** cascade edits into historical video records.

Tags are separate entities identified by ID and unique (`name`, `type`): `technique`, `skier` and `custom`. Current tag management principally exposes custom tags. The detail `TagSelector` manages associated tag IDs while `TechniqueSelector` owns the modern technique-name UI. Do not confuse the old `technique` tag type with current JSON technique selections.

Favorite resorts are **names only**, not an association/favorite flag on a video and not a duplicate resort dictionary. They make resort choice faster; deleting a favorite does not erase resort names already stored on videos.

## Localization

- `src/i18n/index.ts` creates an `i18n-js` table with `ja` and `en` and sets fallback to Japanese.
- `expo-localization.getLocales()[0].languageCode` chooses `ja` if Japanese; all other device languages choose English.
- The choice is made **once when the module loads**; the app has no live language picker or subscription. Switching device/app language is handled by iOS restart.
- React uses `useTranslation()`, which returns stable `t` and `locale`; non-React modules import `t` from `@/i18n`.
- `src/i18n/locales/ja.ts` defines the structural `Translations` type and `en.ts` is statically constrained to it. Add keys and plural variants to **both** at the same time.
- `locales/ja.json` and `locales/en.json` are **iOS/Android permission-description localization**, distinct from runtime translation TS files. `app.json` retains a Japanese `infoPlist` fallback.
- Date/time formatting uses locale-aware helper functions, and the calendar's day labels/week titles adapt accordingly.
- No user-facing text should be hard-coded into components when it can use a translation key; duplicate candidate reasons are typed stable keys rather than translated text generated by service logic.

The new engineering specifications are English, but this does **not** mandate translating existing Japanese public text, historical design notes, the app's Japanese strings, or comments.

## Visual and interaction system

`src/constants/colors.ts` defines the **Alpine Blue** palette (primary blue, glacier/snow backgrounds, gold accents, semantic tags/status, resort dots). `src/constants/icons.ts` defines semantic icon names, and `src/components/ui/Icon.tsx` wraps `expo-symbols` with fallback behavior. `GlassSurface` and its `.web` companion separate native visual effects from browser rendering.

`src/constants/motion.ts` provides shared Reanimated spring contracts:
- `SPRING_DEFAULT`: critically damped (damping ratio 1), nominal 350ms;
- `SPRING_MOMENTUM`: damping ratio 0.8 for momentum gestures only;
- `LAYOUT_SPRING`: springified layout transitions;
- `SPRING_PRESS_IN`: nominal 150ms;
- `PRESS_SCALE = 0.97`.

`PressableScale` centralizes touch feedback. `hapticsService` provides light/medium/selection/success/warning/error wrappers, swallowing unavailable-native errors. ESLint prohibits direct app-wide imports of `expo-symbols` and `expo-haptics` except their designated wrappers. Follow `.memory/apple-design-rn.md` for historical implementation reasoning when changing transitions, and validate Reduce Motion on iOS.

The tab bar uses `NativeTabs` with SF Symbols and iOS platform rendering; it is not a promise that every individual component uses the latest Liquid Glass treatment. Related improvements remain open in Issues #45–47.

## Accessibility and input

Buttons used for critical actions should provide semantic accessibility roles, labels and selected state as applicable. The source has some explicit roles and labels, but **do not claim full VoiceOver coverage** based solely on a green TypeScript build. For changes to selection modes, nested gestures, charts or form inputs, check VoiceOver navigation/announcement and keyboard behavior on device.

The detail editor must preserve focus through background refreshes; its memo entry scrolls to stay visible above the keyboard, and it supplies an iOS keyboard accessory. The search filter uses draft state and 400ms debounce; it must not lose an explicit clear/reset operation to a delayed stale callback.

## Preferences and compatibility

Every setting is a string in `app_preferences`. UI hooks and services provide typed parsing/defaults; unknown values must not accidentally imply new permissions. In particular, `media_priority` has **no default** in its service, because choosing `save_space` without consent would impose a future network policy. Other historic UI settings can have explicit defaults (`home_sort_order = newest`; `weekStartDay = monday`). The obsolete `app_locale` key is cleaned up on startup.

A new preference requires: documented exact key and allowed values, default/invalid-value behavior, migration treatment, UI labels in both locales, and tests of persistence/restart.
